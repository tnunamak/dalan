# Changelog

This file lists user-visible changes, newest first. Check the section for your target release before you upgrade.

## 0.7.1

- **A refused `dalan service install` leaves no public route.** Install now runs every check that only reads (the worker profile, the home, the service package link, unit file names, Gozar's state path and the user systemd manager) before it asks Gozar for a route. Before, a failed check could leave a public route that nothing recorded. `--write-units-only` no longer asks Gozar for a route. If install fails after the route exists, the route stays and is recorded in the service receipt, so `dalan service uninstall` removes it.
- **Install names two common setup problems.** A `--home` whose admin socket path is too long for the system (107 bytes on Linux, 103 on macOS) is refused first, with the length, the limit and the fix: a shorter `--home`. A user systemd manager that cannot be reached is named, with `systemctl --user status` to see why and the note that a login session or `loginctl enable-linger` may be needed.
- **`dalan doctor --auth` explains your own pairing window.** When a pairing window for the same worker is already open, the check still fails and leaves the window alone, and now says it is your own window: finish pairing the client, or run `dalan connect stop`, then run doctor again.
- **A command with `--home` no longer runs the default home's version.** `dalan` hands each command to the version that the default home's service runs. With `--home DIR` (or `--home=DIR`) you name another home, so the installed `dalan` now runs the command itself. `DALAN_HOME` works as before.
- The [local-agent requester guide](docs/local-agent-requester.md) now passes the brief in single quotes, so the shell cannot run `$(...)` or backticks from it, and shows how to write a single quote inside the brief. It also no longer says that `report.summary` is always one line.

## 0.7.0

Install, run and update Dalan with three commands on Linux and macOS:

```
npm install -g @tnunamak/dalan
dalan service install --worker NAME --route tailscale
dalan connect start --worker NAME
```

- **One command installs a service on macOS and Linux.** `dalan service install --worker NAME --route ROUTE` creates a systemd user service on Linux or a launchd LaunchAgent on macOS, publishes it through [Gozar](https://www.npmjs.com/package/@tnunamak/gozar), and prints the public address, where the private connector URL file is, the next command and a health check. Run it again and nothing changes. It asks for your approval of the route first; `--yes` approves after you have read the disclosure. An address you already serve stays possible with `--public-url`, `--port` and `--target`.
- **One default home.** Commands find the service home without `DALAN_HOME`. Install records it in a small pointer file (`~/.config/dalan/home`); `DALAN_HOME` still overrides it. `dalan service uninstall` removes the service, its update timer or agent and its route, and moves the home aside to `<home>.removed-<date>` instead of deleting your keys and job history.
- **Automatic updates on macOS too.** A launchd update agent checks once a day, like the systemd timer on Linux. If an automatic update fails, the updater rolls back to the previous version on both systems. The `dalan` command on your PATH follows the version the updater switched to, so the command and the service do not drift. `DALAN_NO_FOLLOW=1` turns that off.
- **Updates work on npm 12.** `dalan service update` downloads the release tarball itself, checks it against the registry's sha512 integrity and installs from that local file. npm 12 refuses a remote tarball URL as a dependency (`EALLOWREMOTE`), which would have stopped every automatic update.
- **Updates adopt older services.** `dalan service update` now adopts a service installed by 0.6.0 or 0.6.1, including a unit that names its package directory with a trailing slash and a server that has no update gate.
- **Any OAuth MCP client can connect.** Dalan accepts a client it has not seen before when its redirect address is a plain HTTPS address or a native loopback address, and the owner approval code stays mandatory. The consent page and `dalan connect pending` show the client name as untrusted text, the redirect host and the full redirect address. The older callback allow-list still loads and only adds entries.
- **Routes only through Gozar 0.2.** Dalan no longer starts tunnels or runs Tailscale commands itself. It asks Gozar for the route, shows the disclosure Gozar returns, and never falls back to another route. `--route` takes a name you configured in Gozar or the label of an offered route, such as `tailscale`. Tailscale Funnel never replaces an existing listener on this device. A session route (such as `dalan try`) uses port 8443, or 10000 when 8443 is in use, and never 443. A service route takes the first free port of 443, 8443 and 10000.
- **`dalan doctor --auth`** runs the OAuth sign-in flow (discovery, registration, PKCE, token, MCP initialize and tool list) against the public address and prints a PASS or FAIL line per step without printing a secret.
- `dalan submit --wait` prints the request ID and the worker prompt before it waits. The guides now show `claude mcp add --scope user`, how to retry with `--replace`, and that Node 24 or newer is required.
- Documentation uses only the commands above. `worker-bridge-setup.mjs` remains for older setups and is no longer in the guides.

Upgrade note: `@tnunamak/gozar` 0.2.1 is now a dependency (`^0.2.1`). A service that a release before 0.7.0 generated keeps working; move it with a fresh `dalan service install`.

## 0.6.2

- Add `dalan service update`, `--check`, automatic-update on/off and update status for Linux systemd services. New installs enable daily checks with jitter. Releases install side by side with npm integrity checks, local self-checks and a complete tool-catalog comparison for each configured worker. Changed descriptors stage until an explicit `--yes`; refresh hosted connectors after that switch. Failed switches attempt to restore the previous package and saved persistent state, and report rollback failures. See [service updates](docs/service-setup.md#service-updates) for limits and enrollment of older services.
- A candidate release is now checked with synthetic keys made for the check. It never receives the service keys.
- An interrupted update is recovered when the service starts (`dalan service recover` runs before the server), not only at the next update. It does nothing while an update is running.
- While an update switches, the restarted bridge refuses worker calls, OAuth requests and owner commands with a retryable 503 and runs no background writer until the update commits or rolls back. A rollback can no longer lose a change that was acknowledged.
- A release that was rolled back is skipped by the daily timer until a newer release or a different package appears. `dalan service update --retry` tries it again. `dalan service status` shows the failed release.
- The first `dalan service update` adopts a service installed by 0.6.0 or 0.6.1 and keeps the node binary its unit uses.

## 0.6.1

- `dalan service install` now uses the Gozar that ships with Dalan. A `gozar` command on `PATH` is no longer required. An explicit `--gozar-bin` still wins; otherwise Dalan uses the bundled copy, then `GOZAR_BIN`, then `PATH`. If none is found, the command stops before it creates any unit.
- `dalan service install` now checks Gozar's state path before it creates units or starts anything. Gozar refuses a state directory with a group- or world-writable ancestor, such as `~/.local` at mode 775. Dalan now stops first with one line that names the directory and the `chmod go-w` command to run.
- When another program replaces the Tailscale Funnel rule of a stopped trial, Dalan leaves it alone and no longer prints a command that would switch off that port.
- Muse is now described as the cloud agent at muse.ai in the Muse and worker-client guides. These guides also say that either a Tailscale route or the Gozar relay can supply public HTTPS.
- Documentation fixes: the generated service environment list in the upgrade guide is complete, the old-package command list matches the one at the top of that guide, and the local MCP guide tells you to use the Home line a public trial prints.

## 0.6.0

- Run one long-lived bridge for several named workers with built-in OAuth and a stable worker catalog. `dalan service install` creates a systemd user service on Linux and registers an existing HTTPS origin with Gozar. See [service setup](docs/service-setup.md).
- Migrate existing worker settings with `dalan service migrate-workers`. It reads source files without changing them and copies only effective repository grants supported by audit records. It denies and reports unaudited additions. It does not copy connections, tokens, jobs, results or old destination approvals; pair each connector again and approve new destination revisions.
- Add read-only policy work orders. Submit one result to named eligible workers; the first eligible worker to claim it owns that job. Destination approvals remain tied to each worker's reviewed revision. See [pool submission and worker flow](docs/pull-queue.md).
- Start a hosted MCP trial with `npx -y @tnunamak/dalan try`. It prints the connector URL, asks for terminal approval and returns the connected agent's demo report. The `--local` option runs a self-check on this computer without opening a public route.
- In `auto` mode, a saved Gozar choice or an older saved localhost.run choice selects Gozar. Otherwise Dalan uses Tailscale when a route is usable, and Gozar when Tailscale is not usable. When Gozar is selected, Dalan names tunnl.gg, links its [terms](https://tunnl.gg/terms) and [privacy notice](https://tunnl.gg/privacy), and asks for consent before exposure. After consent, Gozar creates an installation-owned key for its key-bound `tunnl-gg` relay. Dalan does not pass your SSH keys. The relay terminates TLS and can see the connector URL and traffic.
- A temporary demo link can change or stop without warning, including within minutes. Dalan checks the original address and ends the trial when it detects a route change or loss. The trial ends after three hours at most; that limit does not promise that the link will last that long. `npx -y @tnunamak/dalan setup` can save Tailscale or Gozar for public trials. An explicit `--route tailscale` stops with an explanation if Tailscale cannot start; it does not fall back to a trial link. The explicit `--route localhost.run` option remains available.
- On stop, Dalan closes its forwarding gate and attempts to remove its route. If it cannot confirm cleanup, it reports that and prints a recovery command. It removes the connector URL file. For temporary routes it also removes the bridge secret; a reusable Tailscale home keeps its bridge configuration.
- Tailscale trials use port 443. Dalan opens its own Funnel rule and attempts to remove only that rule when it stops. If another rule holds port 443, Dalan can start an isolated temporary node without changing that rule. The node may need a one-time sign-in and uses a new address. If its public address does not answer, the trial prints `TLS certificate: ok` or `TLS certificate: error (...)` and keeps a masked `tailscaled.log` in the trial home.
- Ctrl-C cancels a route that is still starting. The trial's readiness check verifies OAuth metadata before it prints that the public route is ready.
- Hosted-trial clients that negotiate SSE now receive a heartbeat every 20 seconds while an authenticated request is in progress; JSON replies are unchanged. `t3_thread_wait` defaults to 90 seconds and stops at that limit, returning partial state. The legacy catalog keeps its existing 120-second descriptor.
- The worker tool list changes once in this release. After upgrading, refresh the Dalan connection once in each worker client.

## 0.5.2

- Fix: a queued job that a worker had skipped is no longer marked skipped again as soon as it expires and is requeued. A job is marked skipped, and lists behind newer jobs, after it has been claimable for 10 minutes without a claim. The expiry requeue cleared the skip mark but kept the time the job first became claimable, so the next listing marked it skipped again at once and it stayed behind every newer job. The requeue now also restarts that time and the job's listing count.

## 0.5.0

- Packaging: the repository root no longer has the `dot-bridge.service`, `dot-bridge-selfcheck.service` and `dot-bridge-selfcheck.timer` links; the files stay in `systemd/`. If an installed unit is a symbolic link to one of the root paths, point it at the file in `systemd/` and run `systemctl --user daemon-reload` before you update the checkout ([setup reference](docs/setup-reference.md#legacy-service-examples)).
- Fix: `--purge-home` no longer misses a service file that names the bridge home through a directory name with `,`, `:` or `=` in it. The unit check now reads such a path in a unit or plist; before, the path was cut at those characters, so a unit that named the home through such an alias was missed. A unit with more possible paths than the check reads in bounded time now refuses the purge as unreadable.
- Fix: `--purge-home` now also refuses when another unit names the bridge home through a different spelling of the same directory, such as a path through a symlinked parent. Before, only the exact text of the path was matched, so such a unit was missed and its home could be deleted while the unit stayed installed.
- Fix: `worker-bridge-setup --remove --purge-home` now refuses a `--home` that reaches the bridge home through a symbolic link, such as a linked parent directory, and names the real path to use instead. Before, the unit and open-database checks compared the alias with the real path, did not match, and the purge deleted the real home while a bridge could still be using it. Nothing is removed when it refuses.
- Fix: a registered secret in a JSON text that is a single string, written as `"\u0073..."`, is now masked like one inside an object. Redaction now also inspects such a text in its decoded form.
- Fix: the worked backup recipe in `docs/operations.md` now stops when `lsof` reports an error, not only when it finds a process holding a database; before, a failed check counted as "nothing open". Run the recipe as the service user or as root.
- Fix: `worker-bridge-setup.mjs --remove --purge-home` now keeps the bridge home whenever it cannot be sure that nothing uses it. Before, a missing `lsof` (macOS), an `lsof` that timed out or failed, or an unreadable `/proc` (Linux) was read as "no process holds `bridge.db`", and the home was deleted under a running service. A failed check now stops the purge, keeps the home and says why; only a check that ran to the end and found no holder lets the purge go on. The unit-file check now follows symlinks, so a unit linked into the user's unit directory that names the home blocks the purge, and a unit file or directory that cannot be read blocks it too. A link to `/dev/null` (a masked unit) or to nothing is ignored. On Linux, a process that refuses the check (another user's, or one that is not dumpable) is skipped, because the bridge is a plain node process. In the upgrade guide, the service-file commands (`--repoint`, `--remove`, `--write-units-only`) are exempt from the bridge-`HOME` prefix, since they look for the unit files under your own `HOME`. Tool names and schemas are unchanged.
- Security: a worker can no longer add audit rows or replay finished registry calls without limit. The registry tools `call_tool_read` and `call_tool_write` now share one admission budget of 120 calls per minute for each verified worker, checked before the tool lookup, the refusal, an idempotency replay and the audit write. Before, a worker with no grant could call a missing tool without limit and add one `tool_registry_log` row per call, and a granted worker could replay a finished `idempotency_key` without limit, because the 30-per-minute limit of each tool ran only after those steps. A call over the budget is refused with `rate_limited` and writes no audit row; the bridge counts it in one `admission_refused:WORKER` row of `tool_registry_meta`, which survives a restart (the minute window does not). Tool names, descriptions and schemas in `tools/list` are unchanged.
- Fix: a secret in a worker's JSON report is now masked even when one character of it is written as a `\uXXXX` escape. Redaction now inspects JSON text in its decoded form. A worker could write a registered secret, a known token format or a credential field name into a JSON report with one character written as a `\uXXXX` escape, and it passed into the owner report and other sinks unmasked. Such text is now masked; JSON with nothing to mask keeps its formatting. Redaction still cannot stop deliberate disclosure through unrecognized transformations, including base64 encoding of an unregistered secret; SECURITY.md and `docs/redaction.md` say so. Tool names and schemas are unchanged.
- Fix: the restore check (`restore-check.mjs`) now catches a wrong `as-storage.key`. It authenticates the built-in authorization store with `as-storage.key`: it opens the storage verifier and every sealed row read-only, as the store's own start does. Before, it reported `as.sqlite` as `ok, key present` for any 32-byte key file, so a wrong key passed the check and the service then refused to start. The check still does not prove that the whole service starts; [Operations](docs/operations.md) describes the isolated start that does. It now reports `ok, key verified`, or fails with `authorization storage cannot be decrypted with the restored key`. Tool names and schemas are unchanged.
- Fix: under an external OAuth issuer, a subject that the operator did not name for a worker can no longer reach it. A `workers.json` connection record must now name `subject`. Before, a record with only `issuer` and `connection_id` matched any allowed subject that presented that `connection_id`, so a subject the operator never named for the worker could reach it. A workers file with such a record now fails at startup with `workers: NAME: every connection record needs a subject`; add `"subject": "<the token's sub claim>"` to each record (`client_id` and `connection_id` stay optional extra pins). The legacy profile (no workers file) and built-in OAuth are unchanged; tool names and schemas are unchanged.
- An operator-registered tool can no longer use a schema `pattern` that makes validation slow. Schema `pattern` now admits only one closed form: `^`, an optional literal prefix of letters, digits, `_` or `-`, one character class (such as `[a-f0-9]` or `\d`) with one quantifier (`+`, `*`, `{n}`, `{n,m}` or `{n,}`), then `$`. Examples: `^[a-f0-9]{64}$`, `^[A-Za-z0-9_-]+$`, `^job-[0-9]{1,8}$`. Such a pattern matches in time linear in the input. Before, a bounded backtracking check admitted patterns such as `^a*a{0,16}a{0,16}a{0,16}a{0,16}$` and `^a*a{4000}b$` that blocked validation for one to six seconds on long strings. Any other pattern is refused at registration with a message naming the allowed form. Tool names and schemas in `tools/list` are unchanged.
- Fix: a worker's `finish` no longer loses a completed report to a fixable summary problem. A missing, empty or blank `summary` is now taken from the first non-empty line of `result` (capped at 4096 bytes) and the receipt carries `summary_derived: true`; a `summary` over 4096 bytes is cut and marked `summary_truncated: true`; a `progress` note over 4096 bytes is cut and marked `note_truncated: true`. Refusals that must stay (empty or oversize `result`, bad `outcome`, too many `artifact_ids`, empty `note`, a second different report, progress on a finished job) now say the next call and what to change. Claim, connection and destination checks are unchanged. The advertised `finish` and `progress` schemas match: `summary` is no longer required, and the schemas for `summary` and the `progress` `note` accept up to 262144 bytes (before, 4096), so a client that checks arguments against `tools/list` no longer refuses these calls before the server repairs them. The server still stores at most 4096 bytes of each, and `result` stays at 262144 bytes. This changes the advertised tool list: workers see it after the one-time connector refresh of this release (refresh the Dalan connection in each worker client once). Tool names and every other tool are unchanged, and `legacy-v46` keeps its frozen schemas.
- Fix: a message that a worker queues for a T3 thread is no longer posted twice, and a failing post is no longer retried about 60 times an hour. In registry `t3_post` delivery, only one flush runs at a time per tool, worker and thread, and each flush selects its rows after it holds the turn, so concurrent calls and the minute timer no longer post the same queued message twice. Timer retries now count against the same 6 per hour and 30 per day budget and are logged in `tool_post_log`; a failing `t3-post` can no longer be retried about 60 times an hour. A failure other than `t3-post` exit 3 may have delivered the message, so the row is marked possibly delivered and is never retried automatically; `dalan tool list` reports the count. Tool names and schemas in `tools/list` are unchanged.
- Fix: a removed, revoked or disabled operator-registered tool can no longer leave an old message that a later registration or grant delivers. A tool removal, revoke or disable now commits together with the discarding of the messages queued under it, and registering a name discards any unsent rows left under it, so a crash cannot leave an old message that a later registration or grant would deliver. Queued messages the timer can never deliver (no thread, or no enabled granted tool pointing at their thread) are now discarded instead of staying queued forever. Tool names and schemas in `tools/list` are unchanged.
- Fix: a crash during a sign-in approval no longer leaves a connection whose sign-in can never finish. The built-in authorization server marked a connection attempt done before it stored the interaction result, so a crash between the two left an approved connection whose sign-in could never finish (the browser got "already finished"). The attempt is now marked done only after the result is stored. A retry of the same page finishes the flow for the already-approved connection, with no second approval and no second connection, and a repeated visit after the flow ended is refused. Exact code, worker, window and redirect checks are unchanged.
- Fix: a tool that posts a T3 message can no longer be registered as read-only. In the registry, a handler kind now declares its effect class, and registration refuses a class that does not match. A `t3_post` tool must be class `write`; before, it could be registered as `read` and `call_tool_read` would then post a message. A stored `t3_post` tool whose class is `read` is listed and enforced as `write`, so `call_tool_read` is refused (`wrong_class`) and a write call needs the `schema_hash` and `idempotency_key`. Tool names and schemas in `tools/list` are unchanged. `docs/worker-clients.md` now has one "Operator-registered tools" section for the add, grant, call, revoke and remove steps, and `docs/t3-reverse-control.md` states the correct `owner_message` limits.
- Fix: a message that a worker queued through `t3_post` no longer reaches a thread after the worker's grant or the tool is gone. This closes three registry safety gaps. Messages a worker queued through `t3_post` are now dropped when its grant is revoked or the tool is disabled or removed, and the timer delivers a queued message only while the tool is enabled, the worker is granted and the tool still points at the thread it was queued for, so a removed tool re-registered under the same name for another thread can no longer receive old text. Tool names and schemas are unchanged.
- Removed: the OpenAI allow-list updater is no longer part of Dalan. This removes `docs/openai-allowlist-updater.md`, `scripts/update-openai-allowlist.mjs` and the matching systemd unit and timer. It was a deployment-specific helper, not part of the bridge.
- Fix: on macOS, a generated service now starts at load and restarts after a crash even while the desktop session is idle or locked. Generated launch agents now list the `Aqua` and `Background` session types, and setup loads and starts them in the `user/UID` launchd domain instead of `gui/UID`. A `gui/UID` domain whose desktop session is idle or locked can be in on-demand-only mode, where launchd neither starts an agent at load nor restarts it after `kill -9` (`KeepAlive` has no effect). `--remove` stops an agent in either domain. Services that an earlier release set up keep running as before; `worker-bridge-setup.mjs --repoint --worker NAME` brings their plist up to date.
- New `worker-bridge-setup.mjs --repoint --worker NAME` points an existing service at the code that runs the script. Use it after `npm uninstall -g dot-bridge && npm install -g @tnunamak/dalan`, which is now the documented npm upgrade ([upgrade guide](docs/dalan-upgrade.md#upgrade-an-npm-install)): the old package leaves its `dot-worker`, `dot-deadman` and `dot-heartbeat` commands on `PATH` until you remove it; Dalan installs only `dalan` and `dalan-*` commands. The guide also corrects the macOS restart after `bootout` (`launchctl bootstrap` before `kickstart`, which otherwise exits 113).
- `scripts/upgrade-drain.mjs` is now part of the npm package, so the documented pre-upgrade drain exists in an npm install.
- `worker-bridge-setup.mjs --repoint` now changes only `WorkingDirectory` and the script argument. A HOME or log path below the old code directory used to be rewritten. It also adds the macOS session types when the code directory did not move, so the upgrade guide runs it on every source upgrade.
- `worker-bridge-setup.mjs --remove --purge-home` refuses, and names what it found, while another unit file in the user's unit directory names the home or a process holds its `bridge.db` open. It no longer needs to know the launchd label of a release before 0.4.0 to avoid deleting a home under a running service.
- Fix: `dalan wait --drained` could leave two waiters running for one producer, or report `already_running` when nobody was waiting. The waiter slot is now a directory that a waiter takes with one atomic rename; a stale entry is removed by its own unique name, so no waiter can remove another waiter's entry, and a waiter that dies at any step leaves nothing that blocks its replacement.
- Add `dalan mcp`, a local stdio MCP server with `dalan_submit`, `dalan_wait`, `dalan_result` and `dalan_status` tools, so a local agent (Claude Code, Codex) can use the bridge as tool calls. Each tool runs the matching CLI command through the admin socket. The worker-facing endpoint and its tool catalog are unchanged. See `docs/local-agent-mcp.md`.
- The worker tool list changes once in this release: refresh the Dalan connection in each worker client once after you upgrade. This is the last planned change to the tool list. This release (catalog v2) supersedes the announced `list_files` cursor change. It keeps the worker tools `t3_thread_create`, `t3_thread_send`, `t3_thread_wait` and `t3_thread_set` as top-level tools, advertised only with `DALAN_ENABLE_T3_TOOLS=1`. Adds MCP `annotations` to every tool and three fixed registry tools: `list_tools` (read-only), `call_tool_read` (read-only) and `call_tool_write`, each taking `{tool, arguments}`. Future abilities are registered server-side and never change the tool list. `legacy-v46` is unchanged. Add future abilities by registering tools, not through tool names, descriptions or schemas.
- A new database no longer contains the name of the first worker. The columns that record which worker owns a job or message start with an empty default instead of `'dot'`, the break table is `worker_breaks` (was `dot_breaks`), and the skip marker on jobs is `assignments.skipped_at` (was `skipped_by_dot_at`). The fix-loop source is stored as `fix-loop` in new databases; databases created earlier keep `dot-fix` in their stored rows and schema, and both spellings are still accepted as input. Schema version is now 66, adding policy work orders. Upgrading renames the table and column in place and keeps every row's worker. **Rolling back after this upgrade needs the backup taken before it**, because older code looks for the old names. Databases that already reached schema 35 keep `DEFAULT 'dot'` in their stored schema text; every insert names the worker, so the default is never used.
- Fix: a check job that the [owner integrator](docs/owner-integrator.md) creates can no longer be claimed by a worker named `dot`. These check jobs were stored as belonging to the worker `dot`. They now belong to the reserved owner `unknown`, which no worker can claim.
- Fix: a worker session that stopped responding no longer keeps its jobs for the length of a usage break. A claim whose worker made no claim-bearing call for one lease period is now released even across a usage break. Before, the sweep was held during a break and the end of the break (owner clear or the worker's next tool call) extended every ordinary worker deadline by the break's length, so a dead worker session kept its claimed jobs for the lease plus the break. Only the claimant's own calls extend a lease; `list_pending` never does. Tool names and schemas are unchanged, so no connector refresh is needed.
- The earlier alias of the `notify_owner` MCP tool is removed. `notify_owner` is the only notification tool and keeps its schema, authorization, audit and retry ledger. The tool catalog changes for the default `stable`, `questions-v1` and `protocol-v0` profiles (`legacy-v46` never listed the alias). A client that cached the old tool list keeps working without a refresh; only a call to the removed alias fails, with `unknown tool`. Refresh the connector when convenient to drop it from the list.
- Workers that follow wake signals now take the oldest job first, so older jobs no longer expire behind newer ones. The wake sent when a job is submitted now names the oldest queued job the worker may claim, not the new job, so workers that follow wakes claim oldest first and older jobs no longer expire behind newer ones. `finish` responses that name `next_queued` now tell the worker to claim it before its run ends, and the `assignment_expired` error tells the worker to call `list_pending`. Who may claim what is unchanged.
- The guides now show how to run Codex CLI as a worker without a screen, and how to upgrade, check and uninstall an installation. They cover Codex CLI non-interactive approval for the worker tools (per-tool `approval_mode`, no bypass flag), login order and `--skip-git-repo-check`; source-install upgrade, macOS restart, first-job smoke check and one uninstall inventory.
- Fix: `submit` no longer fails with "not a git repository" after a temp cleaner deletes a repository mirror's files. The bridge re-initialises a repository mirror whose directory exists but is not a valid repository (for example after an age-based temp cleaner deleted its files), so `submit` no longer fails with "not a git repository". The next fetch refills the mirror.
- A claim refused because the bridge is paused now says the pause is temporary and tells the worker to call `list_pending` and claim again later. `list_pending` adds `claims_accepted` and, when work is queued and the worker has free slots (`free_lanes`), `next_queued` and `next_action` naming the oldest queued jobs; while paused it says not to claim yet. Tool names and claim schemas are unchanged.
- `dalan` with no arguments now prints short grouped help (getting started, everyday, operator) instead of one long usage line. An unknown command prints one line that names it, suggests a close match and points to `dalan --help`, and exits 1. `dalan help --all` lists every command, and `dalan COMMAND --help` or `dalan help COMMAND` shows a command's usage. Command behaviour is unchanged.
- A job with no delivery option now defaults to `none` (read results with `wait` and `get`), and unsupported destination modes are rejected. The T3 delivery adapter loads only for an explicit T3 destination.

- `dalan try` now cleans up after the repository step: it revokes the demo grant, deletes the demo repository and the request files when it exits, and does the same at the next start if a run was killed. It also checks that a second repository is still refused after the grant, and stops the repository setup on Ctrl-C.
- Security: request logs now mask credential values by field name. Opaque credential values are redacted at the request-log sink before JSON serialization.
- Fix: a bridge restart no longer restarts the claim lease clock, a notification is not sent twice, and a job cannot be cancelled while its result delivery is uncertain. Notification idempotency keys are reserved before publishing, cancellation is blocked while result delivery is uncertain, and claim lease deadlines persist across restarts. A usage break never moves a claim's lease deadline.
- Fix: a paused service or a slow delivery can no longer hold up lease expiry. Lease, preparation and skip maintenance run on an independent timer.

- Host checks: a stop is now reported as verified only with durable evidence from the host. In receipt mode, the bridge requires durable host stop evidence before accepting a verified stop; it scans nested cgroups, refuses stop verification without a sandbox scope, uses pidfd signaling, and uses monotonic stop deadlines. Full-tree cancellation is reported as verified only for the systemd backend.

- `dalan try` now also runs a repository job. It builds a one-commit demo repository in the trial home, shows that a job for an ungranted repository is refused, grants the demo repository with `dalan worker allow`, and lets the demo worker claim, read and finish a job on it. The trial bridge turns repository workspaces on (256 MiB free-disk floor) and redirects only `dalan-demo/hello` to the local copy; no other repository is reachable until granted.

- The Claude Code guide now documents a native worker (`claude mcp add`, `/mcp`, `dalan connect approve`) without T3 Code.

- On macOS, `worker-bridge-setup.mjs --start` now also runs `launchctl kickstart` after `bootstrap`. On macOS 26 a bootstrapped agent could stay loaded and never run, so the bridge did not answer after "Started".

- The pre-upgrade drain can no longer wait without end: the pause and active-claim commands share one time limit, and a timeout prints how to resume the old service before retrying.

- A native client, such as Codex CLI or Claude Code, on another computer can now sign in to a remote HTTPS bridge. The owner allowlists its native loopback OAuth callback, with exact canonical host and path, random client ports, a redirect typo check and out-of-band pairing-code approval. Native pairings are approved one code at a time: a newer native attempt never supersedes or blocks an older one, and `dalan connect pending` prints each native entry's approve command. Web pairings keep newest-only approval.

- A new profile no longer shows or defaults to the legacy worker name `dot`: `tell` without `--worker` now follows the same rule as `submit` (the only worker, or a clear error), and the top-level `status` fields report scope `none` instead of `dot` unless a worker named `dot` is configured.


- Fix: a repository grant (`dalan worker allow`) now takes effect only after its audit event is recorded. If its audit event cannot be written, the grant is not applied and the command says "repository grant not applied". Before, the grant stayed in force with no audit record. A removal still takes effect first and reports a missing audit event, because failing closed is safe.

- Add `dalan try`: one command that creates a private trial home, starts the loopback bridge, pairs a built-in demo worker through the real OAuth flow and finishes one job. It then queues a second job for the owner's own worker, asks before approving that worker's pairing, and prints its report. `dalan` now also reads `DALAN_HOME` as its `HOME`; the server still reads `HOME`.

- Dalan is published to npm as `@tnunamak/dalan`. The npm package excludes generated Python caches; package checks confirm that it ships no tests, fixtures or local state and that shipped modules have resolvable relative imports. `dalan try` also reads `connect pending --json`, shows the resource line (or says the bridge did not report it), refuses a home that already holds files it did not create, stops on ended input or Ctrl-C at any step, retries a lost port race, and has the demo worker open an MCP session before it calls tools. A relative `DALAN_HOME` is resolved against the current directory.

- A fresh install's heartbeat can now ping without a drainer: drainer evidence is opt-in with `DALAN_DRAINER_HEALTH_FILE`. The bridge status gate remains mandatory; opted-in evidence retains fail-closed freshness and health checks.

- Security: a worker connection that was revoked or replaced can no longer act on a claim. The bridge fences every built-in worker call that acts on a claim to the recorded, currently live connection, checked where the effect commits: renew, progress, ask and consume, finish (legacy and native, with stored replay and late evidence after a cancel), native `artifact_chunk` and upload, all five workspace tools (reads included), and claim activity. A revoked, replaced or other connection gets `connection_not_live` and no claim-scoped state change (no claim, workspace, report, notification or artifact row, no file of the job, no claim activity counter); legacy `finish` now captures its patch artifact inside the finish transaction, after the check, and checks again after its `makeRoom` await. Per-worker call accounting, `sweepExpired` and `makeRoom` cleanup still run before the check and are system effects. `get` still reads for anyone but moves the note-seen cursor only for the live holding connection. Pre-schema-61 NULL-bound claims must expire before reclaim. See PROTOCOL.md, Connection fence.

### Upgrade

- **Upgrade action:** installs that relied on the drainer gate must set `DALAN_DRAINER_HEALTH_FILE` to their evidence file (the `drainer-health.json` written with the data root; default `~/.local/share/dot-bridge/drainer-health.json`) before restarting, or the heartbeat will ping on bridge health alone.
- Before upgrading, drain or cancel queued and running jobs for workers that declare a destination. Unapproved jobs are refused when they next need a claim, and built-in authentication now includes live connection IDs in the destination revision. Review the current destination and resubmit refused work under a new request ID; approvals cannot be changed in place.

### Changes

- Security: the development flags that allow unauthenticated or insecure public access now work only on loopback. `DALAN_DEV_ALLOW_UNAUTHENTICATED=1` and `DALAN_ALLOW_INSECURE_PUBLIC=1` are restricted to loopback binds (`127.0.0.1`, `::1`, `localhost`). On any other bind host, including the `0.0.0.0` default, startup now fails instead of serving an unauthenticated public route, and neither flag waives the TLS reverse proxy requirement for external OAuth.
- Operations documentation now says that a future-schema refusal makes no schema or row changes, though SQLite may manage WAL sidecars.
- Fix: a resolver failure is reported once per listing even when it returns a Promise or throws a falsy value. Restoring an approved destination clears the listing block only while repository policy still allows the job.
- Fix: the self-check now accepts a resource with a path and rejects an origin-only match. It compares the OAuth metadata `resource` with the whole configured resource, as RFC 9728 requires, instead of its origin. A path resource now works and an origin-only value no longer matches it.
- Fix: the daily self-check no longer accepts an issuer that only appears inside another string. It requires the issuer to be an exact member of the metadata's `authorization_servers` array in the daily self-check. A string that only contains the issuer no longer matches.
- Redaction now detects Slack rotating tokens, Telegram and Discord bot token shapes and URL credentials with short passwords.

- Redaction now masks private-key armor with ASCII and Unicode dashes. It retains the existing ASCII matcher, which can also mask ordinary hyphenated prose.
- Redaction refuses very long runs of combining marks: to bound normalization work, inputs with over 64 consecutive raw or compatibility-normalized combining marks are refused and masked in full.
- Redaction now detects and masks Slack incoming-webhook URLs, JWTs and Google OAuth client secrets, access tokens and refresh tokens.
- Worker-visible output now masks secrets held in object keys, matching admission, which already refused them.

## 0.4.0

### Upgrade

Dalan is the new package and command name. Dalan installs only the `dalan` and `dalan-*` commands; the command names of the `dot-bridge` package are not installed. Use `DALAN_X` settings; a defined new name wins over `DOT_BRIDGE_X`, including an empty value except `AUTH_MODE`: empty new auth falls back to a non-empty legacy mode, so a template cannot disable built-in auth. A real legacy fallback emits at most one main-thread warning per process.

Before restarting an existing installation, set `DALAN_ENABLE_T3_TOOLS=1` if its pinned catalog advertises the T3 reverse-control tools, and retain the worker capability and catalog profile. Inspect the exact repository list seeded once from each legacy worker's claimed jobs and still-live queued jobs; add any further owner-approved repositories explicitly. A non-loopback external-OAuth HTTP listener also needs `DALAN_TRUST_PROXY=1` and an HTTPS reverse proxy. Authentication-off development flags are refused in production.

Fresh homes use Dalan directories. Populated legacy roots, including OAuth keys, clients, tokens, path secrets, queued jobs and delivery ACKs, remain in place; an empty new root, or one that lacks a listed durable component, cannot hide them. Unlisted files are not merged or recovered, so verify a migration with `dalan paths`. Startup never moves or merges data. Follow [the upgrade guide](docs/dalan-upgrade.md) for explicit path migration, consistent backups and rollback. Database schema is 60; upgrading from 0.2.0 still requires the schema-49 backup procedure below.

Refresh non-legacy connectors and restart their worker conversation to discover the Dalan name/version and `notify_owner`. An older alias of the notification tool remains with the same schema, authorization and durable retry ledger (removed in a later release). With the T3 retention setting, existing tool names and schemas remain available. The `legacy-v46` profile preserves its captured twelve-tool catalog and server identity. Existing OAuth scope strings, issuers and resource URLs do not change.
