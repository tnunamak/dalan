# Worker connection longevity

A worker’s OAuth token, refresh token and event subscription have separate lifetimes. Dalan does not hold or refresh the worker client’s token. The client must refresh its credentials and renew a finite Events subscription before its advertised `refreshBefore` deadline.

For an external issuer, inspect its access-token lifetime, parent session limits, refresh-token reuse policy and offline-session limits. A client-session timeout cannot necessarily extend the parent session. If you enable offline access, verify the issuer’s idle and maximum lifetimes and the client’s refresh behavior. Do not copy another deployment’s scope mappings, and do not treat a working subscription as proof that token refresh works.

The bridge defaults Events subscriptions to seven days and returns an expiration in `refreshBefore`. Its monitoring reports missing or expiring subscriptions. A manual or scheduled pull worker can operate without an Events subscription; assess health against the worker mode you configured. See [pull workers](pull-workers.md).

The legacy `dot-bridge-selfcheck.timer` example and `scripts/daily-selfcheck.mjs` are deployment-specific, so review their repository and subscription assumptions before you use them. Set `DALAN_GITHUB_REPOSITORY` and `DALAN_SELFCHECK_REPOSITORY_ID` (the numeric GitHub repository ID pinned to this installation) in the service environment, for example with a systemd drop-in, before enabling it. The check reads the public resource and the issuer from the bridge's own OAuth file (`oauth.env`, which must be mode 0600 or it is treated as unavailable), and the TLS host defaults to the resource hostname, so no endpoint environment variables are needed (the repository settings above stay required). `DALAN_SELFCHECK_RESOURCE` and `DALAN_SELFCHECK_ISSUER` override the file; an explicit `DALAN_SELFCHECK_TLS_HOST` must equal the resource hostname or the check fails. An alert is sent once per distinct set of failures: a repeated identical failure still exits 1 but sends no new alert until the set changes.

## MCP failure diagnostics

After deployment, `~/.local/state/dalan/requests.jsonl` records `mcp_received` before authentication and one `mcp_outcome` when each HTTP response finishes or closes early. A generated `call_id` joins those records to `mcp_inbound`, which still means authentication and request parsing succeeded. A received call with no outcome can indicate a process exit. These MCP records omit URLs, tokens, subjects, client-provided names, RPC IDs, arguments, file paths, contents and exception messages; the one exception is `tool_error_message` on a failed tool call, the bridge's error text redacted like alert notes and cut to 300 characters. Declared methods and tools are retained; undeclared names are logged as `unknown`. Old records are not rewritten. A refused sign-in has an `mcp_outcome` with `http_status` 401 and an `auth_reason`: `missing_bearer`, `invalid_token`, `unsupported_signature`, `invalid_signature`, `jwks_unavailable`, `signing_key_unavailable`, `wrong_issuer`, `wrong_audience`, `malformed_claims`, `expired`, `not_yet_valid`, `unknown_subject`, `invalid_scope`, or for built-in sign-in `connection_inactive`. A request to a path that is not the MCP path logs `mcp_inbound` with `status` 404, `route` `other`, `http_method`, `path_shape` and `auth_header_present`. `path_shape` keeps only the names of public routes (`mcp`, `.well-known`, `oauth-protected-resource`, and similar) and replaces every other segment, including the secret path and any token in a wrong URL, with its length. A client with no `mcp_received` line at all never reached the MCP path.

Outcome fields include tool, HTTP status, JSON-RPC error code, tool `isError`, duration, response bytes, completion (`finished` or `closed`), request phase, and fixed authentication/JWKS reasons, timing and fetch status. `pending` auth/JWKS outcomes with null timing mean the connection closed while verification was still running. `http_status: null` means no headers were sent; it must not be treated as HTTP 200. `response_bytes` is the serialized JSON body size prepared by the bridge, excluding HTTP headers. A closed response may not have delivered all those bytes. `finished` means Node handed the response to its transport; it does not prove ChatGPT accepted it. A pre-auth or incomplete-body failure has no tool name. Authentication is logged separately from tool scope rejection, which remains an HTTP 200 MCP tool error with the authentication challenge in `_meta`.

For an intermittent failure, correlate progress timestamps with `mcp_outcome` and reverse-proxy access entries. Check authentication failures first, then closed responses and their phase, then JSON-RPC or tool errors and response sizes.

## Liveness classes and alerts

The bridge reports observations and labels, not diagnoses. `dalan status --json` adds `claimed_outer_count`, `max_claimed_outer_assignments`, `oldest_claim_age_ms`, `oldest_claim_progress_age_ms`, `last_worker_call_at`, `last_list_pending_at`, `oldest_unclaimed_event_2xx_age_ms`, `queue_classes` and `stale_claims`. Queued work after its first event 2xx is labelled:

| Class | Meaning | Default threshold (limits.json key) |
| --- | --- | --- |
| `pause_suspected` | no worker tool call and silence at least the threshold; cause unconfirmed | 20 min (`pause_suspected_silence_ms`) |
| `at_capacity_healthy` | every active worker subscriber has no free lane after counting shared worker claims and its principal's historical subject claims for that worker, and the newest activity on at least one claim is within that claim’s stored lease; waiting is expected | 60 min by default (`claim_lease_ms` sets the maximum) |
| `stale_claims` | claim past its persisted lease deadline, the deadline the sweep uses (`lease_expires_at`); `get` does not extend it | per grant (60 min by default) |
| `alive_not_claiming` | the worker called tools recently, slots free, item still queued after 2x the interval | interval 10 min (`assignment_reannounce_interval_ms`) |
| `transport_failing` | no event for the item ever got a 2xx; separate path, no re-announce | 20 min (`pause_suspected_silence_ms`) |

**Recover a claim.** Run `dalan claims` to inspect active grants. Automatic abandonment happens after the persisted lease expires; a usage break does not extend it. Regrant still requires verified host stop and resolved delivery/admission gates. `dalan abandon ID` needs the operator key and does not shorten the old deadline or prove that remote compute stopped. See [Claims and leases](operations.md#claims-and-leases).

**After a restart.** A claim last touched before startup is not swept until startup plus that claim's own lease duration. A claim touched since startup gets no restart grace. The first maintenance tick after the applicable deadline performs the sweep. Native protocol claims require explicit `renew_claim`; ordinary activity does not extend their fixed deadline.

**Queued work.** Preparation expiry and default-worker skip expiry continue during pause or a usage break. The PR-head reviewer cancels work for merged or closed PRs. See [Jobs the worker never takes](pull-workers.md#jobs-the-worker-never-takes) and [PR-head reviewer](pr-head-reviewer.md).

**Alerts and wake-ups.** The liveness classes above are observations, not proof of a cause. Attention alerts require 30 continuous observed minutes before publication; a recovery notice follows only an alert that was sent. `denial_mentioned` is log-only. Queue re-wakes are normally limited to one event per subscription every 90 seconds, with older work backing off after two hours. Pause, full capacity, inactive subscriptions and unresolved delivery can suppress them. For exact eligibility, settings and terminal transport behavior, see [Lifecycle events and metrics](operations.md#lifecycle-events-and-metrics).

## Change and rollback

Back up configuration and state before changing issuer mappings or service settings. Record the original values and restore only the changed mappings if a test fails; restoring an entire identity-provider database would also erase unrelated later changes. Test a full worker login, job completion and token refresh after any authentication change. Follow [operations](operations.md#upgrade-and-rollback) for bridge rollback, preserving existing unit names and data roots.

Self-check metadata discovery inserts `/.well-known/oauth-protected-resource` before the resource path: `https://h/api` uses `https://h/.well-known/oauth-protected-resource/api`; a root resource uses `https://h/.well-known/oauth-protected-resource`. The metadata `resource` must equal the configured `DALAN_SELFCHECK_RESOURCE` exactly, as RFC 9728 section 3.3 requires; an origin-only value does not match a path resource, and a root resource must be spelled as the server publishes it (with or without the trailing slash). Metadata and JWKS probes reject redirects without following them and identify the failing setting without disclosing the redirect URL.
