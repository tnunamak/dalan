# Built-in authorization server: concrete profile

This guide describes the built-in authorization server and its connection flow. The goal is that an operator can connect a cloud worker (ChatGPT, Claude, Grok) to a bridge without a hosted identity provider or a homelab; external issuers stay supported.

Path examples use fresh-home defaults. For an existing installation, resolve the actual roots with `dalan paths --json`: populated legacy roots remain active, as the [upgrade guide](dalan-upgrade.md) describes.

In this guide, `<home>` means the bridge service's private home and `<config>` means `<home>/.config`. Resolve an existing installation's active roots with `dalan paths --json` rather than assuming these defaults.

## Components

- Protocol engine: `oidc-provider` 9.13.0 (panva; dependencies koa, jose, debug). We mount it on the bridge's public HTTP listener through `provider.callback()` under `/<secret>/oauth`. The issuer is `<public origin>/<secret>/oauth`, and this is the only OAuth implementation. The bridge implements no OAuth protocol cryptography; its storage adapter encrypts persisted state. The bridge resolves opaque access tokens through the provider and checks their grants and approved connection records. External OAuth keeps its existing JWT verifier.
- Storage: an oidc-provider adapter on `node:sqlite`, file `<config>/dalan/as.sqlite`, mode 0600. Models: Client, Grant, Interaction, AuthorizationCode, RefreshToken, Session.
- Keys: on `dalan as-init`, generate an ES256 (P-256) JWKS in `<config>/dalan/as-jwks.json` (0600) and a cookie key file (0600). Plain files, not Keychain: launchd agents run unattended, and Keychain prompts would block them. Rotation: `dalan as-rotate-keys` adds a new `kid` and signs with it. Stop the bridge before rotation. Retired signing keys and cookie keys remain for their issued-token and browser-session lifetimes plus clock skew.

## Connect a worker

1. For a fresh installation, follow [service setup](service-setup.md#owner-setup), which creates the worker profile and built-in authorization state. For an existing built-in installation, keep its home, profile and public URL; do not rerun `init` or `as-init` merely to connect another client. An intentional issuer or endpoint change needs the [upgrade and recovery procedure](dalan-upgrade.md). The issuer is `<public origin>/<secret>/oauth` and the resource is `<public origin>/<secret>/mcp`.
2. The owner starts a tunnel or reverse proxy that serves public HTTPS and supports the OAuth browser flow, and forwards only the public listener, never the owner socket. Preserve the public `Host` (including a non-default port); a mismatch returns 421, and forwarded headers do not override it. See [the exposure Host rule](../README.md#expose-your-bridge) and [service setup](service-setup.md) for network configuration. Issuer and resource come from config, never from forwarded headers.
3. Run `dalan connect start --worker NAME` before adding the connector in the vendor UI. The default pairing window lasts 10 minutes. The vendor reads the path-suffixed protected-resource metadata and AS metadata, then uses Dynamic Client Registration (DCR) to register the client. DCR needs the secret namespace and an open window; registration creates no authority. A vendor that cannot register itself can use a static public client that the owner creates (see [Owner client commands](#owner-client-commands)).
4. The vendor opens the browser at `/<secret>/oauth/auth`, with PKCE S256, `resource`, scopes and redirect. For a native client with a loopback callback, open the sign-in page on the computer running that client's callback listener. For a hosted client, use the provider's browser sign-in flow. The interaction page shows a short pairing code (for example `KTBX-4QPM`) and an instruction to run `dalan connect approve KTBX-4QPM --worker example-worker` on the bridge computer. The page waits.
5. The owner runs `dalan connect pending`. It shows each pending transaction: full pairing code, client_id, untrusted client name, exact redirect URI, worker, scopes and age. For native clients it warns that identity is not verified: host and name prove nothing. The teammate must read the pairing code from the browser page on their own machine and tell the owner over a trusted channel. `--confirm-redirect` checks for a redirect typo only; it is not identity proof. Approval of a native callback also requires the exact host, port and path: `dalan connect approve CODE --worker NAME --confirm-redirect URI`. Native entries are approved one code at a time: a native entry is never superseded, a newer native attempt never blocks or replaces an older one, and approving one code approves no other. `dalan connect pending` prints the approve command, with the redirect, for each native entry, so match the code and the redirect to the teammate. A web entry follows a different rule: only the newest web pending entry of a worker can be approved, and older web entries are shown as superseded because an app that registers again abandons its older attempts. A native entry never supersedes a web entry. If the code matches no pending entry, run `dalan connect pending` and compare the codes before retrying. The approval:
   - is bound to the interaction UID, which already binds the client, redirect, PKCE challenge and resource;
   - is single use and expires after 10 minutes;
   - creates a Grant and a bridge **connection record** `{connection_id (uuid), worker, client_id, redirect_uri, resource, scopes, created_at}`. When the worker already has an active connection, the new one replaces it only after a second confirmation (`--replace`). The old connection is then revoked.
6. The interaction completes. The vendor gets a single-use code and exchanges it with its verifier. Access tokens are opaque, bound to the exact resource, and valid for one hour. Refresh tokens rotate on every use.
7. Every MCP request: resolve the opaque AccessToken through the provider; check account, resource, expiry and scopes; then check its grant and approved connection. The active connection resolves the worker. `dalan connect revoke NAME` takes effect immediately, before the access token expires.

In built-in mode a grant records the connection it was given to (`claims.connection_id`, schema 61). A duplicate `claim` or native receipt replay is accepted only from that connection while it is live and, when the owner approved a destination, only while the live connection set matches the approved digest. The same connection check also gates every later call that acts on the grant: `renew_claim`, `progress`, `ask_question`, `consume_answer`, `finish` (fresh, replay and late evidence after cancel), `artifact_chunk`, and the workspace tools `list_files`, `read_file`, `apply_patch`, `run_check` and `workspace_result`. The Store runs it in the transaction that writes the effect, after the claim check and before any state change, and a call from a revoked, replaced or other connection fails with `connection_not_live` and changes nothing. Checks on the claim come first, so a wrong subject or worker, a superseded claim or an expired lease keeps its own error. `get`, `list_pending` and `ack_message` stay open to any authenticated worker connection; `get` moves the note-seen cursor only for the live holder. Under external OAuth (no connection id and no liveness check) the check does not run for a claim that stored no connection. A claim that stored a `connection_id` (for example, a database that moved from built-in to external OAuth) is refused with `connection_not_live` until its lease expires, because external OAuth presents no connection. In built-in mode a grant made before schema 61 records no connection, fails the check, and waits for its lease to expire. See [Connection fence](../PROTOCOL.md#connection-fence-built-in-mode). See [current connection limits](../PROTOCOL.md#claims-and-worker-tools).

The local CLI approval is the owner authentication. There is no password and no browser account. The interaction page can approve nothing by itself.

## Owner client commands

- `dalan connect add-client --redirect-uri URI [--name NAME] [--json]` creates a persistent static public client and prints its `client_id`; it creates no secret and grants no authority. The redirect URI must match the configured callback allowlist, using the same exact callback check as DCR. This command is available through the owner Unix socket only.
- `dalan connect clients [--json]` lists static and DCR clients with their type, client ID, untrusted name, redirect URIs and creation time.
- `dalan connect remove-client CLIENT_ID` removes a static client. It revokes that client's grants and connections, so the existing revocation path retires its subscriptions. DCR clients cannot be removed with this command.

A client still needs an open pairing window and owner approval before it can receive tokens or access a worker. The public HTTP listener has no static-client creation route.

## Settings (oidc-provider)

`features.registration` on (no initial access token); `features.resourceIndicators` on, with one allowed resource and `accessTokenFormat: 'opaque'`; `features.revocation` on; `features.devInteractions` off; `pkce.required` always and S256 only; `rotateRefreshToken: true`; `clientDefaults` with `token_endpoint_auth_method: 'none'` for public clients; `features.clientIdMetadataDocument` (CIMD) **off** in the first release (experimental in 9.x). Exact redirect matching (the oidc-provider default). TTLs: AuthorizationCode 600 s, AccessToken 3600 s, RefreshToken 30 days (inactivity), Interaction 600 s.

## Secret namespace and discovery

The explicit connector setup exposes the private resource URL to the chosen application. Treat the URL as a secret; ordinary pending and connection lists omit it. The AS encrypts OAuth state with `as-storage.key` in its private state directory. Back up the AS database and key, bridge database and its `.secrets/storage.key` together: losing the key prevents recovery of existing sessions. Schema 52 introduced encrypted subscription storage; this release uses schema 66. Older code may refuse or be incompatible with migrated state. Follow [upgrade and rollback](operations.md#upgrade-and-rollback) and restore the matching pre-upgrade recovery set rather than lowering the schema number. Migration scrubs the managed SQLite database and its WAL, but does not erase older backups, snapshots, or copies.

For resource `https://bridge.example/<secret>/mcp`:

- Protected-resource metadata: `/.well-known/oauth-protected-resource/<secret>/mcp` (RFC 9728).
- AS metadata: `/.well-known/oauth-authorization-server/<secret>/oauth` (RFC 8414).
- OpenID discovery aliases: `/.well-known/openid-configuration/<secret>/oauth` and `/<secret>/oauth/.well-known/openid-configuration`.
- Every discovered protocol endpoint, interaction and browser resume route stays under `/<secret>/oauth`.

The root `/oauth` surface and unsuffixed well-known routes return 404 in built-in mode. No vendor-specific root fallback is enabled. All secret-bearing metadata has `Cache-Control: no-store`; the public AS also sends no-referrer and other security headers. The MCP challenge advertises the suffixed protected-resource metadata URL. Legacy and external-OAuth metadata and listener settings are unchanged.

Claude's documented discovery sequence tries path-suffixed protected-resource metadata and keeps the path in its `resource` indicator (see [Claude authentication documentation](https://claude.com/docs/connectors/building/authentication)). In oidc-provider 9.13.0, `Provider` derives its mount path from the issuer; `pathFor` prepends it to endpoint and resume routes. We strip exactly that prefix for its router and map RFC 8414 discovery back to its internal well-known route. `scripts/builtin-as-exposure-test.mjs` verifies a full DCR → browser pairing → owner approval → token → MCP initialize using only discovered URLs. This proves that the bridge serves suffixed metadata that matches the documented discovery sequence.

## Admission limits and recovery

DCR accepts five POST attempts per pairing window by default, including invalid or incomplete requests. The budget is reserved before body parsing and persists across restarts; concurrent requests cannot oversubscribe it. Live interactions and pending pairing codes each have a default cap of five. These defaults allow a single-owner pairing and retries without granting anonymous callers the previous 100-client/25-interaction budget. The existing total client cap of 100 and 24-hour stale-client purge remain as final storage bounds.

Set optional `as.json` fields `"limits": {"registrations": 5, "interactions": 5}` to change these caps. Each value must be an integer from 1 to 100. Restart to apply changes. Registration bodies are at most 8 KiB, validated client metadata at most 4 KiB, client names at most 128 characters, and redirect lists at most eight URIs of 512 characters each. Chunked bodies have the same byte cap; exceeding it closes the request.

Registration outside a window returns 403; an exhausted DCR budget returns 429; full interaction capacity returns 503. Busy pages instruct the owner to run `dalan connect reset`. A flood of registrations followed by authorization attempts during an open window can leave more than one pending pairing for the same worker. The pending list follows the approval rules in step 5 of "Connect a worker". A flood can fill the pending cap of five and make new attempts fail with a busy page, but it cannot take the approval of another native entry; run `dalan connect reset` to clear it. If an entered code does not match a pending entry, the CLI says to run `dalan connect pending` and compare codes. `dalan connect reset` remains available to clear unapproved clients, pending pairings and their interactions, then restore the registration budget in the current window. It preserves approved connections, grants, tokens and attempts whose approval has already started, including the provider record needed by a pending browser resume redirect. It does not open or extend a window. Requests started before reset cannot repopulate the cleared state. Repeating `connect start` extends an open window and keeps its budget and attempts. Stop/start opens a fresh budget and clears pending interactions from earlier windows; use reset to remove unapproved clients too.

## Public HTTP deadlines (built-in mode)

The loopback public listener sets `headersTimeout = 10,000 ms`, `requestTimeout = 30,000 ms`, `keepAliveTimeout = 5,000 ms`, `maxConnections = 128`, and socket inactivity timeout `180,000 ms`. Node checks incomplete requests every 1,000 ms, so deadline enforcement can lag by that interval. The header and body deadlines are absolute: sending a byte every few hundred milliseconds does not extend them. Ten seconds permits normal tunnel headers; thirty seconds permits bounded MCP uploads while limiting stalled bodies. Five seconds recycles idle keepalive connections; 128 sockets leaves room for normal parallel MCP calls with bounded exposure.

`requestTimeout` limits receipt of the request, not tool execution or the response lifetime. The three-minute inactivity timeout covers stalled sockets and leaves headroom around `t3_thread_wait`: non-legacy catalogs advertise and enforce a 90-second default and maximum; `legacy-v46` keeps its frozen 120-second descriptor, while the server caps its effective wait at 90 seconds. On the hosted trial, a POST that accepts `text/event-stream` negotiates SSE only after bearer authentication, JSON-RPC validation and confirmation that the request has an ID. The response starts with a comment and sends comment keepalives every 20 seconds, followed by one final `event: message` JSON-RPC response. When SSE is not negotiated, normal MCP request/response calls keep JSON responses. SSE disables socket inactivity expiry when headers are sent, so the response has no total deadline; open streams still count toward the connection cap. Legacy and external-OAuth listeners retain their prior settings.

## Maintainer conformance checklist

This checklist is for maintainers changing the authorization implementation. To connect a worker to an unmodified release, follow the setup and first-job checks in the [worker guide](worker-clients.md).

1. Authorization without PKCE, or with `plain`: refused.
2. A code reused, a code with the wrong verifier, a code for a different redirect or client: refused.
3. A web redirect URI that differs in any byte (path, port, query, trailing slash, scheme, suffix host) from registration is refused without redirecting. A native callback may vary its port only for registration-to-authorization matching on a remote HTTPS bridge or in loopback mode; scheme, host and exact path stay bound, and token exchange requires the full approved redirect. Native approval requires `--confirm-redirect` with the exact host, port and path shown by `dalan connect pending`; this checks for a typo, not identity. The owner must compare the code the teammate reads from the browser page on their own machine over a trusted channel. A native approval selects only the pending entry matching its code (see step 5 of "Connect a worker"). `localhost` is accepted only after a separate owner allowlist entry; its resolution follows the client machine's host resolver.
4. A `resource` other than the configured one, at authorization and at the token endpoint: refused. A token whose `aud` is a different resource: rejected by the bridge.
5. An approval with an expired, consumed or unknown pairing code: refused. Approval of interaction A cannot complete interaction B.
6. A DCR client with no approval cannot get a token. An anonymous registration has no access.
7. For a public client without sender-constrained credentials, an identical retry of the immediately previous refresh exchange within five seconds returns the same saved token response, while its successor remains unconsumed and the grant and connection remain live. The retry must not rotate again or extend the grace window. A changed request, an older ancestor token, a consumed successor or an out-of-grace replay is refused through the normal replay path and revokes the grant and connection. Verify both the bounded successful retry and the rejected replay cases, including rejection of the old access token after revocation.
8. After `connect revoke`: the next MCP call with a still-valid access token is rejected, and refresh is refused.
9. After a restart: existing tokens still verify (keys persist). After key rotation, tokens signed with the old kid verify until they expire, and new tokens use the new kid.
10. Forwarded-header spoofing (`X-Forwarded-Host`) does not change issuer or resource.
11. Two connections for two workers, with one sub and two clients: each resolves only to its own worker (worker-isolation tests, built-in mode).
12. A static client uses the callback allowlist, has no secret or authority before approval, survives a restart, and is removed with its grants, connections and subscriptions. The public listener cannot create one.

## Wake signal for hook-driven workers

A worker's MCP client may be one-shot, with no push. Its fastest wake can be a timed hook script that holds no connector credentials. The bridge offers that script one public bit in built-in mode only: `GET /signal/<signal-token>`. In oauth and legacy modes the route does not exist (404).

- `dalan connect signal-token [--worker NAME] [--rotate] [--json]` saves the full signal URL (public origin plus `/signal/<token>`) in `~/.config/dalan/signal-url.<worker>` with mode 0600 and prints only that path. JSON output contains the path and non-secret worker, rotation and poll-interval metadata; it never contains the URL or token. Configure the hook to read the URL from that file. The resolved worker name is used in the filename even when `--worker` is omitted. `--worker` is required when the profile has more than one worker; with one worker it defaults to that worker. The first call creates the worker's token. `--rotate` replaces only that worker's token, and its old URL answers 404 from that moment; other workers' URLs do not change. The command uses the owner Unix socket only.
- The token is a separate 256-bit random value (64 hex characters) per worker in `~/.config/dalan/signal-token.<worker>`, mode 0600. It is not the MCP path secret. With no token file, the route answers 404. Migration: a host with one worker and an older single `signal-token` file keeps that URL working for its one worker; that worker's `--rotate` writes `signal-token.<worker>` and deletes the old file. With more than one worker the old file matches nothing.
- A good token answers `200` with exactly `{"work":true}` or `{"work":false}`, plus `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. `true` means at least one queued, live, uncancelled assignment targets the worker that owns the token, or the worker holds its own active claim whose lease has expired and that has had no claim activity for `DALAN_RESUME_IDLE_MS` (default 120000; `0` turns this second case off; see "Resume wake" in `docs/pull-workers.md`); other workers' queues and claims do not show. The answer has no ids, titles or counts. The bridge computes it at most once every 10 seconds per worker and caches the boolean.
- A wrong or missing token answers `404` with an empty body, the same as any unknown path. The token compare is constant-time. A method other than GET with a good token answers `405`. The strict canonical Host check of the other routes applies first (`421`).
- Rate limit, in memory: about one request per 5 seconds per source address with a burst of 3, and 30 requests per minute for the whole bridge. Excess requests get `429` with `Retry-After`. Only requests with a good token count, so a scanner with wrong tokens cannot use up the allowance. The signal rate limiter uses the socket peer's address rather than a forwarded client address. `DALAN_TRUST_PROXY` acknowledges the HTTPS reverse-proxy deployment requirement on a non-loopback bind; it does not give this limiter a forwarded client IP. Behind a tunnel on this computer that is the loopback address for every caller, and the limit becomes one shared bucket.
- The request log gets one line per request: `{kind:'signal', status, work}`. It never holds the token or the path.

For a complete hook example, including transfer of the private signal file and replacement of the `wake` placeholder, see [The wake signal](pull-workers.md#the-wake-signal). Generate the signal file on the bridge host; the worker hook needs only that file.

Treat the URL as a bearer secret: anyone who has it can learn whether work is queued. If it leaks, run `dalan connect signal-token --rotate`. Maintainer check: from a source checkout installed with `npm ci`, run `node scripts/signal-endpoint-test.mjs`. The npm package does not include it; it takes about one minute because it uses the real cache and rate-limit intervals.

## Not in scope

This profile does not cover multiple owners or vendor or model attestation. It also gives no protection against compromise of the owner account, an approved connector or the bridge process; a stolen bearer token is limited only by the 1-hour lifetime and revocation.
